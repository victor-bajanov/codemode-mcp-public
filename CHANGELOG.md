# Changelog

Curated notes for each public release. Newest first. (The auto-generated commit list for a release lives in that release's PR on the public mirror; this file is the readable summary.)

## v1.1.0 — 2026-10-09

**Defensive security review, remediated.** A defensive review on 2026-10-07 found 24 issues across token handling, the sandbox request path and the inspectors, each proved with a local proof-of-concept test. All 24 are now closed: each fix carries unit tests, and every proof-of-concept that demonstrated a weakness has been turned round to assert the control holds, keeping the original attack payload as its regression input. Narrow residuals are accepted and documented (a same-browser double submit of `/callback`, a double click on the consent page's Approve, the shared rate-limit bucket used only when `CF-Connecting-IP` is missing, and KV-backed throttles that are approximate under concurrency), and MCP `scope` stays unenforced by design because authority comes from the surface review.

**Request path: the reviewed operation is the operation sent.** The headline fix. A backslash, dot segment or encoded separator inside a path parameter could make the URL parser rewrite the path after the surface review had matched it, so an allowed operation could reach any other operation with the same method on the origin, and a `?` or `#` could smuggle query parameters past the inspector, the approval dialog and the audit line. The matcher now refuses those segments, the wire path is built from the matched template with encoded parameters, and the built URL is re-resolved and must be the operation that was reviewed, all before inspection, approval or token minting. An encoded `?` or `#` inside a value (`%3F`, `%23`) is accepted and re-encoded, so Calendar ids and file names containing `#` keep working. Alongside it: on inspected and approval-gated operations, a request may use only one of `body`, `bodyBase64` and `multipart`, and raw bytes under any JSON content-type (edge whitespace trimmed; `text/json` and `application/x-json` included) must parse and are judged, shown in the approval dialog and sent as that parsed JSON, while an approval over raw non-JSON bytes that no inspector reads says the body cannot be shown; CR/LF/NUL in multipart part metadata is refused, typed arrays in `body`, `query` or `multipart` are refused in favour of `bodyBase64`, a non-string `method` or `path` gets a `malformed` audit entry instead of a raw `TypeError`, and upstream redirects are no longer followed (a 3xx becomes an `upstream_redirect` error).

**OAuth: a consent page on `/authorize`.** `/authorize` no longer redirects straight to the upstream sign-in. It shows a consent page naming the MCP client, the redirect URI (host in bold, with a warning for unfamiliar hosts) and the scopes, and only the operator's approval, a five-minute single-use form token signed with `COOKIE_ENCRYPTION_KEY` and bound to a `SameSite=Strict` cookie, starts the upstream leg. The form posts back to `/authorize`, so the existing Cloudflare Access application gates both. `/callback` is bound to the approving browser by a second cookie. MCP clients must now use PKCE S256, `/register` accepts `http://` redirect URIs only for loopback hosts, and MCP grants expire 90 days after authorisation (older grants keep no expiry until re-authorised). Together these close the attacker-registered-client route (AUTH-VULN-01). `COOKIE_ENCRYPTION_KEY`, previously asserted but unused, now does real work.

**OAuth: smaller hardening.** Refresh failures read `Refresh failed <status> (<error>)` with no upstream body, `/callback` logs upstream error bodies only under `ALLOW_PII_IN_LOGS`, rate-limit buckets group IPv6 clients by /64, the public `/staging/*` endpoints sit behind a best-effort per-client failure throttle (`STAGING_FAILURE_RATE_LIMIT`, `STAGING_FAILURE_RATE_LIMIT_WINDOW_SECONDS`; it bounds sustained guessing, not a parallel burst) with uploads streamed and cut off at the size cap, the consent page warns about a Claude or loopback host reached under an unexpected scheme, and a provider's `completeAuthHook` can no longer override the user identity or refresh token.

**Sandbox: host-side limits and a read-only `search`.** codemode's 70-second timeout runs inside the sandbox, where the code it limits can disable it. The host now enforces its own deadline (`EXECUTE_HOST_TIMEOUT_MS`, default 75 s) and a per-run upstream budget (`EXECUTE_MAX_UPSTREAM_CALLS`, default 1,000, below Cloudflare's per-invocation subrequest limit). The `search` tool no longer receives `__stagingHost`, which had given it a full upstream channel, and is annotated `readOnlyHint`. Each MCP session is bound to the user who started it, `putFile` checks the size before decoding, and `stageFromUpstreamJson` forwards only its declared options.

**Token broker: one slot per grant.** Two MCP clients for the same user on a rotating provider (Xero, Optical) used to overwrite each other's upstream token slot, leaving one of them failing until re-authorisation. Slots are now per grant (`token-slot:<userId>:<sha256>`, 180-day TTL), the old per-user slot migrates on first use, and an unreadable slot asks for re-authorisation instead of retrying a spent token.

**Gmail and Calendar inspectors.** The outbound inspector now reads headers the way mail servers do: CRLF is read as LF, the header block ends at the first blank line, and a repeated `To`, `Cc` or `Bcc` is denied. A lone CR, or CRLF mixed with bare LF, in the header block is denied (`ambiguous-line-ending`), as is a header name that is not RFC 5322 ftext (`malformed-header-name`). Addresses with two `@`, in quoted or commented forms, or behind a display name that is not a plain phrase (one holding `@`, `:`, `;` and so on) are refused, with a message saying how to write recipients. Filters that add `TRASH` or `SPAM` (Gmail's "Delete it" and "Mark as spam") now need approval; the old check looked for a field Gmail does not have. Filter `action` keys outside the known set are denied (`filter-unknown-action-field`), so `delete: true` is still refused. Calendar attendees flagged as resources skip the allowlist only at `resource.calendar.google.com`, and a Calendar event write whose payload is not a JSON object is denied.

**Xero inspectors.** Xero's JSON parser ignores key case and accepts `"true"` for a boolean, so the draft, credit-note and bank-transaction inspectors now read gated keys case-insensitively, deny two casings of the same key, and treat any gated boolean other than absent, `null` or `false` as set.

**Docs.** `packages/scaffold/SECURITY.md` gains a section on the consent page, client requirements, grant lifetime, session binding, execution limits, the staging throttle and the new KV keys; the README lists the client requirements, the four new optional vars and the behaviour changes above.

**Brand.** codemode has a mark: the "Gate" lockup heads the README (`assets/codemode-lockup.svg`, with the bare mark in `assets/codemode-mark.svg`) and appears inline on the consent page.

## v1.0.0 — 2026-09-24

**Optical provider ships publicly.** This is the headline change, and the reason for the 1.0 version: it is the first public release with all three providers (Gmail + Calendar, Xero, Optical). Optical is a separate, self-hosted scheduling backend. You describe work as tasks with timing constraints, grouped into projects or generated from recurring templates, and a solver packs them into a week that you preview, accept, and commit to Google Calendar. The codemode-mcp provider (`packages/providers/optical`, app `apps/optical`) is published as a reference: it does not come with a hosted backend, and its endpoints ship as `example.com` placeholders. Point it at your own Optical deployment by editing the provider's `apiBaseUrl` and OAuth URLs, or per environment with the `API_BASE_URL_OVERRIDE` / `OAUTH_{AUTHORIZE,TOKEN,USERINFO}_URL_OVERRIDE` Wrangler vars. The app ships with `prod` and `dev` environments, OpenTofu modules for both, and a `scripts/bootstrap-optical.sh` that runs the Tofu apply, KV-id paste, secrets, and deploy in one pass.

**Optical: API surface.** The vendored spec exposes 46 operations across: tasks, templates and projects (CRUD); planning (`resolve` a date window into a proposed plan, list and inspect pending plans, `acceptPlan` / `commit` to write it to Google Calendar, read the committed schedule); scheduling preferences (business hours, meeting policy, per-context config, and solver weights, each with update and reset-to-default); calendar busy feeds (create, list, edit, delete, regenerate secret, where create and regenerate return a single-use `reveal_url` so the feed secret never crosses the tool-call boundary); a public booking page (read and update its config, list bookings taken against it; the new `max_horizon_days` setting lets bookers page further ahead than one window); meeting polls (create, read, update, nudge, cancel, force-resolve); and change tracking (`subscribeWebhook` for a Google Calendar watch channel, `replanNow` to re-resolve on demand). The spec's `info.description` feeds the `execute` hint and the `docs` tool, so the workflow prose tracks the upstream API when you re-vendor it.

**Optical: surface-review defaults.** 44 of the 46 operations are `allow`. Two are `deny`: `getCalendarAccessToken`, which mints a raw Google OAuth token and needs a privileged scope the provider never requests, and `googleCalendarWebhook`, the machine-to-machine push receiver that would let the agent spoof calendar-change notifications. These are not intended to be used by the MCP agent frontend. Writes are kept at `allow` rather than `elicit` because Claude.ai does not render elicitation prompts and would silently soft-deny them. The reviewer notes flag the operations with the widest reach (`updateBookingPage`, which publishes a page anyone can book against; `nudgeMeetingPoll` and `resolveMeetingPoll`, which email third parties) as the first to move to `elicit` once client support lands.

**Optical: OAuth.** The provider uses authorization code + PKCE (S256) against a client registered on your Optical deployment, requesting `scheduler:read scheduler:write`. Refresh tokens rotate on every exchange and go through the shared TokenBroker Durable Object, like Xero, with a 90-day idle expiry. Optical's API is pure JSON, so the app has no attachment-staging bindings.

**Gmail: Subject header repair.** Sandbox code sometimes composed raw MIME with a double-applied UTF-8 wrapper, so non-ASCII characters in the Subject (em dashes, for example) arrived as mojibake. The provider now repairs the Subject host-side on `messages.send`, `drafts.create`, `drafts.update` and `drafts.send`: it unwinds the mis-encoded layers (strict-decode guarded, so genuine Latin-1 text is left alone) and re-emits the header as RFC 2047 encoded-words. The repair runs through a new fail-open `normalizeBody` hook on surface-review entries, applied before inspection, so the elicit dialog and the upstream send see the same bytes.

**Release notes.** This curated `CHANGELOG.md` now ships with each public release.

## v0.4.0 — 2026-08-19

**Docs surface & description budget** — the headline change. Tool descriptions were blowing past what clients comfortably ingest, so the scaffold now generates *compact* tool descriptions that fit a 1,800-character budget, with the full reference moved behind a new `codemode.docs(section)` tool (callable with a bare string, no-arg for the overview). A `buildProviderDocs` builder assembles per-provider documentation from the spec at init time, providers can contribute a `compactHint` (Gmail, Xero), and a shared description-budget test battery plus codemode/SDK drift guards pin the contract so upstream bumps or spec regenerations can't silently blow the budget again.

**Surface-review transparency** — every operation in a provider's spec is now annotated with its surface-review status (`[ACCESS: …]` markers), so the model can see up front whether a call is allowed, needs interactive approval, or is denied — including the caveat that call-time escalation to elicit simply fails on clients without elicitation support. The annotation marker is guarded against collisions with upstream spec prose.

**Gmail: Calendar surface** — the Google Calendar half of the Gmail provider is now exposed to clients: same connection, Calendar reachable under its own path prefix with namespaced operationIds.

**Gmail: per-deployment outbound allowlist & tester deployment** — the outbound recipient allowlist is now resolved per deployment rather than baked in provider-wide, enforcement happens at send time (drafts can be composed freely), and there's a tester deployment variant with its own bootstrap script for onboarding an external tester.

**Attachment staging fixes** — downloads now honor content-type overrides, set `Content-Disposition` properly, and the download path is discoverable by the model instead of needing to be guessed.

**Per-worker Access grants** — `allowed_emails` is now the operator baseline reaching every worker, and a new `extra_allowed_emails` map grants additional addresses per worker only — so a tester can be given `/authorize` on one deployment without inheriting access to the whole fleet.

**Xero** — upstream API rate-limit information is surfaced to the MCP client so the model can back off instead of blindly retrying.

**Scaffold** — `codemode.request` accepts sandbox-supplied `ctx.headers`; several robustness fixes from review (no-arg `codemode.docs()` RPC null-marshalling, docs-tool section enum narrowed to the provider's actual sections).
